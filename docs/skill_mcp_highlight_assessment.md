# Skill + MCP 可插拔能力体系阶段评估

## 现状

基础版 Skill 体系已经落地：

- `document_hot_word_statistics`
- `memory_query`
- 统一 Function Calling 目录
- 统一执行入口

## 目标

把文档热词统计、记忆查询等能力抽象成标准化 Skill，并统一兼容本地函数与远程 MCP 工具，最终由同一套 Function Calling 协议驱动。

## 现有基础

- 已有意图路由：聊天链路会先判断是否进入检索，再决定调用 RAG 或直接回答。
- 已有本地工具封装：`run_rag_tool` 已经把检索流程收口成结构化调用。
- 已有记忆服务：长期记忆、画像记忆、删除与清理都已经独立成服务。
- 已有流式工具事件：前端和后端之间已经在传递 `tool_call` / `tool_result`。
- 已有技术依赖预留：项目依赖里已经包含 `mcp`、`fastmcp`、`langchain-mcp-adapters`。

## 可行性判断

结论：**可行性高，且已完成第一阶段落地**。

原因很直接：

1. 业务边界已经拆开了，工具层可以单独抽出来。
2. 现有聊天链路不是硬编码一条到底，而是有路由和工具执行位点。
3. 本地能力和远程能力的差异，适合用适配器统一成同一个调用协议。

## 现阶段必要性判断

结论：**第一阶段已经完成，远程 MCP 适合进入二阶段**。

当前版本更应该优先保证：

- 检索准确率
- 文档解析和切分稳定性
- 记忆召回质量
- 响应速度和可观测性

当系统开始需要更多“动作型能力”时，这个体系的价值会明显上升，比如：

- 热点词统计
- 记忆查询与回溯
- 后续接入审批、工单、目录同步等外部系统

## 推荐落地方式

1. 先定义统一 Tool Schema。
2. 把现有本地能力先接入为标准 Skill。
3. 再为远程 MCP 工具补一层适配器。
4. 最后再把 Function Calling 作为 LLM 的唯一工具入口。

## 风险点

- 工具类型一多，权限和审计必须补齐。
- MCP 引入后，稳定性会依赖远程服务健康度。
- 如果一开始就做全量抽象，容易把研发资源从主问题上分散走。

## 结论

这条技术路线**值得做，而且基础底座已经搭好**。接下来更合适的方向是继续补 Skill 类型和远程 MCP provider，而不是重写主聊天链路。
